# Staff backend

Serve `/staff/*` from apps/api behind the separate HTTPS ADMIN_ORIGIN. Preserve Host, Origin and cookies at the ingress. Serve `/consumer/*` at WEB_ORIGIN. Use distinct hostnames even in development when possible; browser cookies are host-scoped across ports. There are no public-app links or cross-origin credential grants. The staff shell contains no operational screens.

## Establishing access

Use the root setup script and migrate a disposable loopback PostgreSQL database. For the synthetic environment, run the development seed. It creates six credentialless staff identities including owner@example.test. Staff authentication uses email/password and mandatory TOTP. Supply DATABASE_URL, WEB_ORIGIN, ADMIN_ORIGIN and a dedicated ADMIN_SESSION_SECRET of at least 32 characters. Keep it separate from SESSION_SECRET. Never commit values.

The local operator command `pnpm admin:bootstrap` takes the first owner's email only from ADMIN_BOOTSTRAP_OWNER_EMAIL and a password of at least 16 characters from ADMIN_BOOTSTRAP_PASSWORD. It refuses remote databases and repeated initialization. It can initialize the seed owner's empty credential. Inject these bindings for the command only. Subsequent staff grants use an authorized role operation. Initial randomly generated staff passwords and recovery codes are disclosed once. Use secure out-of-band delivery. No credentials are written to logs.

1. POST /staff/login with the exact admin Origin and a JSON email/password. A successful first factor sets a device cookie and a five-minute challenge cookie. A new enrollee receives the base32 seed for a TOTP authenticator. Use six digits, SHA-1 and a 30-second period.
2. POST /staff/verify with both cookies and the TOTP. Subsequent logins may use an unused recovery code from completed enrollment. Success consumes the challenge and creates a row in staff_sessions. Staff tokens are random; only domain-separated keyed digests are stored. Capture the returned CSRF token for subsequent JSON writes. The initial verified enrollment also returns eight recovery codes. Rotation invalidates all previous codes.
3. Send the host-only `__Host-bhava-staff` cookie with the device cookie. Mutations also require X-Staff-CSRF and the matching Origin. Secure, httpOnly, SameSite=Strict cookies expire after twelve hours; eight hours without use expires a session. The server checks the current role, account expiry and disabled state on every request. Logout revokes the database row. Consumer OTP and consumer session tokens never enter the staff authentication lookup.

Scrypt protects passwords. AES-256-GCM encrypts each TOTP seed with its staff ID bound as authenticated data. Track accepted TOTP time steps to prevent replay; recovery digests are single-use. The staff secret is also necessary to decrypt enrolled factors. Plan a controlled re-enrollment before replacing it. A changed device cookie, user agent or trusted country requires fresh sign-in. Set ADMIN_TRUSTED_COUNTRY_HEADER and TRUSTED_CLIENT_IP_HEADER only behind an ingress that overwrites those headers and blocks direct client access. Without a country signal, only the device binding is available; without a verified IP all callers share one network rate bucket.

Login budgets per fifteen minutes are eight attempts per normalized email and sixty per IP. MFA allows five per challenge and sixty per IP. Exceeding a budget locks that scope until the window resets. Sensitive unmask and export operations allow ten per staff account per fifteen minutes. Production IP allowlisting and external alert delivery are deferred hardening.

## Authorization and data

The route/capability table in apps/api/src/staff/policy.ts denies unlisted roles. Handlers apply row and environment policies inside the same database transaction as their audit append. The SQL layer scopes profiles, fixture IDs, review locales, test jobs, payments and audit events. Use a service account with SELECT/INSERT-only privileges on audit_log. Store UTC timestamps; operator displays use Asia/Calcutta (for example, 00:00 UTC is 05:30 IST). Reasons are short descriptions without personal details or credentials. The server redacts contact-like strings before storing a reason. Logs store digests of IP and user agent. Ticket-related views arrive with R2; support currently sees its own audit events.

Only an owner can publish or grant/revoke the owner role. An owner go-ahead is database-backed, bound to exact operation parameters, single-use and time-limited. An admin can execute a previously authorized revert or hard deletion. Every production flag change, including one executed by an owner, requires a go-ahead. Delete intake deactivates the user; completion cascades personal records and retains an opaque audit target. Exports select only the requested account's public profile and consent columns. No operation edits another person's birth data or issues a session as that user.

The masked directory supports lookup by opaque user or profile ID. Unmask reveals one authorized retained field. Phone and email identities are digests, so the endpoint explicitly reports plaintext unavailable. Fixture profiles use canonical seed IDs. Sensitive inspection of a non-fixture profile records both the reason and inspector access. Inspector evidence explicitly marks the unbuilt engine. A missing generated reading has a null user_saw; a time-unknown profile withholds Lagna evidence. AI review exposes retained model/template metadata. Raw prompts, outputs and historical guardrail counts are unavailable in the issue 02 metadata-only schema.

Only test/development fixture challenges can be generated. For a fixture code to be usable across processes, inject the same development SESSION_SECRET into the consumer and staff API runtimes. Staff authentication still uses ADMIN_SESSION_SECRET exclusively. Payment tests never capture money, live adapter requests report unavailable, and test notification sends record a local receipt. A legal upload hook accepts only a digest of a human-supplied file. Support tickets and analytics are R2.

## Content and public projections

The server reads the repository KB from the checkout root or apps/api working directory. Mount the KB read-only for packaged servers. Pending and approved content live in the original rule_catalogue overlay and review tables. Draft doctrine changes do not write YAML. Validation and publication lint public locale copy and optional free remedies. Native-language reviewers see their assigned Kannada or Hindi strings. Localized edits enter the native queue. Public /consumer/rule-copy returns only the selected text for an explicitly approved overlay; staff evidence and drafts stay out. Public /consumer/flags returns flags for the server's own environment. Keep modern_outer display-only if enabled in a later release.

## API reference and verification

From the repository root run `pnpm api:docs` and open http://127.0.0.1:4080/. Swagger UI loads the local OpenAPI document and bundled assets; requests from this documentation origin are disabled. See [OpenAPI specification](../openapi/admin.json). Run `pnpm test`, `pnpm build` and the Python KB validator as described in the root README. The PostgreSQL tests exercise the HTTP handlers with ephemeral loopback databases and synthetic inputs.
